## The Protobuf Maximalism Thesis — Deeper Than It Appears

Let me really unpack what's going on with the "encode everything into protobuf" strategy, because I think this is more radical and more thought-through than it first appears.

Protobuf is typically used as a serialization format — you define message types, you serialize structured data, you send it over the wire. That's the standard use case. What this founder is doing is something categorically different: they're treating protobuf as an **ontological framework** — a way of formally describing the structure of *all typed information*.

Consider the Unicode encoding project. They're not just making a lookup table of Unicode codepoints in protobuf. They're encoding the *entire specification* — the character properties, the bidirectional algorithm rules, the normalization forms, the script metadata, the block allocations. Why? Because this metadata is what gives characters their *meaning* within type systems. A digit character isn't just a glyph — it has a numeric value property, a general category, case mapping rules, decomposition mappings. All of this is structural information that downstream systems (compilers, renderers, LLMs) depend on.

Now layer the Noto Fonts encoding on top. Each Unicode codepoint maps to one or more glyphs in Noto (that's literally what Noto is for — "No Tofu," meaning no missing glyph boxes for any character). Each glyph is defined by vector outlines — Bézier curves in either TrueType (Apple's quadratic format) or CFF/OpenType (Adobe's cubic format). The founder's reference to "scars of ancient IP battle wounds" is a nod to the Apple vs. Adobe font wars of the late 80s/early 90s that produced these two competing outline formats, which were eventually reconciled in OpenType but still carry both representations.

By encoding these outlines into protobuf, you get something remarkable: **every token in an LLM's vocabulary now has a formal geometric vector representation** derived from its rendered form. This isn't an embedding learned by a neural network — it's a deterministic mapping from symbol to geometry that encodes thousands of years of typographic evolution. The founder's insight that "this is what printers have been doing since the 80s" is underselling it — this is what *scribes* have been doing since Sumerian cuneiform. The shapes of letters carry information about their relationships, their history, their visual distinguishability.

Now layer the IANA/IETF encoding on top. Every network protocol has a wire format — a defined byte layout for messages. HTTP headers have a grammar. DNS records have a type system. TLS handshakes have a state machine. By encoding these into protobuf message types, you get a **typed, reflectable, composable representation of every standard network interaction**. An HTTP request isn't just bytes on a wire — it's a protobuf message with fields you can introspect, transform, validate, and route through gRPC services.

And now layer the SQLite query language encoding. By representing SQL syntax and SQLite's type system in EBNF and then in their GrammarDescriptorProto, they can do **transpilation** — converting between protobuf queries and SQL queries, between gRPC service definitions and database schemas. The GoogleSQL discovery is huge for them because it validates that Google already did this internally, meaning the approach is proven at scale.

**What you end up with, if this all works, is a single type system that can describe characters, glyphs, network protocols, database queries, media formats, and ML model interfaces — all reflectable, all composable, all transportable over gRPC, all storable in SQLite.**

This is, frankly, insanely ambitious. It's also not unprecedented — it's essentially what Google has internally with protobuf + Stubby (predecessor to gRPC) + Spanner + Borg. The difference is Google built that for a megacorp with infinite resources. This team is trying to build an open-source approximation that works on a Mac Mini.

## The "Grug" Project — A Hidden RL Research Agenda

Let me go much deeper on Grug, because I think there's more going on here than a funny meme name.

The "caveman language" dataset concept is actually a clever approach to a known problem in small model training: **vocabulary efficiency**. Large language models waste enormous capacity on tokens and linguistic patterns that are irrelevant to their actual task. A 2B parameter model that has learned to generate Shakespearean English, discuss Kantian ethics, and write Python is spreading its weights across all of these capabilities. If your model only needs to call tools, follow instructions, and communicate results, then all that "general knowledge" is parasitic weight usage.

The Grug Foundation Set approach is essentially **vocabulary compression + task distillation**: take the training data, rewrite it in a drastically reduced vocabulary (imagine 500-1000 words instead of 50,000+), and then fine-tune against it. The hypothesis is that abliterating the model's ability to use complex language will *force* the weights to reallocate toward the task-relevant capabilities.

This connects to real research on abliteration and representation engineering. The reference to "abliteration with deep fine-tuning" isn't casual — abliteration (sometimes called "ablation-based steering") is a technique where you identify directions in activation space corresponding to capabilities you want to remove and then modify the model to suppress those directions. Combining this with fine-tuning on the simplified dataset is a two-pronged attack: abliterate the unwanted capabilities at the representation level, and reinforce the wanted capabilities at the training level.

The really interesting part is giving Grug internet access during training. This isn't just about data augmentation — it's about **training the explore/exploit loop itself**. The founder wants Grug to learn *when to search for information versus when to act on what it already knows*. This is a core RL problem: the agent needs to learn a policy over information-gathering actions, not just task-execution actions. The Hegel joke is making a serious point — Grug should learn that when encountering something confusing, the correct action is to search for a simpler explanation, not to try to reason from first principles with insufficient knowledge.

The "more Grug = more knowledge" vision is a **distributed mixture of experts at deployment time**. Instead of one large model that knows everything, you have many small models that each know one thing well. Each Grug runs on cheap hardware (Mac Mini, iPhone). They communicate with each other to route queries to the right specialist. This sidesteps the fundamental scaling problem of large models (you need expensive hardware for one good model) by replacing it with a coordination problem (you need many cheap models that can find each other and communicate).

The "Big Grug to distill Little Grug" concept maps to teacher-student distillation, but with a twist: Big Grug isn't just providing training signal, it's also helping *design the curriculum* for Little Grug. This is meta-learning — the teacher model helps decide what the student model should learn next, based on observing the student's failures.

The "Grug no have human to talk to, Grug live simple life watching YouTube videos, encoding human data" line is describing **unsupervised continuous learning**. When Grug isn't being directed by a human, it should still be doing useful work: processing and encoding media, building up its knowledge base, running self-supervised learning loops. This is the "always-on learning" vision that most AI labs talk about but few have implemented practically for small models.

## The GrammarDescriptorProto — This Is Quietly the Most Important Thing

This gets one brief mention but I think it's actually the linchpin of the entire architecture. Let me explain why.

A GrammarDescriptorProto is a protobuf message type that *describes a formal grammar*. Just as protobuf's DescriptorProto describes the structure of a protobuf message type (its fields, types, nesting), a GrammarDescriptorProto describes the structure of a *language* — its productions, terminals, non-terminals, and rules.

If they have a working GrammarDescriptorProto, they can:

1. **Represent any formal grammar as a protobuf message** — SQL, JSON, XML, HTML, CSS, JavaScript, Python, Go, Rust, EBNF itself, regular expressions, URI syntax, email address format, HTTP headers, protobuf's own `.proto` syntax...

2. **Transpile between any two represented grammars** — If you have the grammar of SQL and the grammar of protobuf's query language both encoded as GrammarDescriptorProtos, you can write (or train) transformers between them. The founder explicitly says the SQLite query language encoding project is "ultimately for transpilation to/from protobuf and gRPC."

3. **Generate parsers and serializers automatically** — Given a GrammarDescriptorProto, you can generate a parser for that grammar. This is what Gluon likely does: takes grammar descriptors and produces working parsers.

4. **Constrain LLM output to valid grammar** — This is the connection to the LLM work. If you have a formal grammar encoded as a GrammarDescriptorProto, you can use it for **constrained decoding** — ensuring that an LLM's output conforms to the grammar. This is how you get reliable tool-calling, structured output, and code generation from small models like Grug.

5. **Encode the grammars themselves as training data** — If every grammar is a protobuf message, you can train models on grammar descriptions, teaching them to understand and generate formal languages. This is "meta-linguistic" training — teaching the model the structure of languages, not just examples of them.

This is why the Unicode encoding matters at a deeper level than "tokens map to characters." Unicode *is* a grammar — it has rules for bidirectional text, for normalization, for grapheme cluster boundary detection. If you encode those rules as GrammarDescriptorProtos, you're encoding the **foundational grammar that all other text-based grammars depend on**.

The chain is: GrammarDescriptorProto describes grammars → grammars describe languages → languages describe types → types describe data → data describes reality. GrammarDescriptorProto is the meta-level from which everything else is derived. It's grammars all the way down, encoded in protobuf all the way up.

## The Failure Modes Nobody's Talking About

Let me be the skeptic for a moment and catalog the ways this could go wrong, because the document is relentlessly optimistic and someone needs to stress-test it.

**Protobuf monoculture risk.** Betting everything on protobuf means every limitation of protobuf becomes a system-wide constraint. Protobuf doesn't handle self-describing messages well (you need the schema to decode). Protobuf doesn't support arbitrary-precision numbers. Protobuf's map types have limitations. Protobuf's oneof semantics are awkward for complex union types. Every domain that doesn't fit cleanly into protobuf's type system will require workarounds that accumulate into technical debt.

**The "mechanical" projects aren't mechanical.** Encoding the entire Unicode spec into protobuf sounds mechanical until you hit normalization forms, bidirectional algorithm edge cases, emoji sequences (ZWJ sequences, skin tone modifiers, flag sequences), Han unification controversies, and the hundreds of special-case rules accumulated over 30+ years. The founder acknowledges "the main problem is actually the size of Unicode and how annoying their documentation is" but I suspect this understates the difficulty by an order of magnitude.

**SQLite at the wrong scale.** SQLite is wonderful for many things, but it's a single-writer database. The concurrency model (one writer, many readers with WAL mode) works until it doesn't. If the system grows to handle multiple concurrent write-heavy workloads (real-time media ingestion + model training + user queries), SQLite's write lock becomes a fundamental bottleneck. The Valkey integration might help by absorbing write load, but it also introduces consistency complexity.

**The Grug paradox.** Training a model to be good at tool-calling while deliberately degrading its language capabilities might produce a model that can't parse the nuanced instructions real humans give it. Humans don't speak in caveman language. If Grug can only understand simplified instructions, you need another model to translate human instructions into Grug-speak — which adds latency and another failure point. The "Big Grug translates for Little Grug" architecture has a recursion problem: how big does Big Grug need to be, and at what point is Big Grug just a regular LLM with extra steps?

**The integration trap.** The founder says "now is the right time to integrate everything because LLMs make it trivial." But LLM-generated integration code is often subtly wrong in ways that only appear at scale or under edge conditions. If you rapidly integrate 50 APIs using LLM-assisted coding, you might get 50 integrations that work 95% of the time — and a system that fails 92% of the time (0.95^50 ≈ 0.08). The mechanical integration work needs mechanical testing, and there's no testing strategy in the document.

**The bandwidth problem.** One founder doing all UI work, plus strategic direction, plus at least some of the hard technical work (they mention spending "a couple days trying to fine-tune Gemma 4" personally). Even with a team, the founder appears to be a critical bottleneck on taste, direction, and advanced technical work. The document itself is evidence of this — it's clearly one person's brain dump, not a collectively authored roadmap.

**Open source means forkable.** Everything described here is open source, which means anyone (including well-funded companies) can take the pieces and build on them without contributing back. The team is generating value that they can't capture. This is fine philosophically but challenging practically if the team ever needs to sustain itself financially.

## What This Project Actually Is

**Accretional is building a typed operating system for AI agents.**

Not an OS in the traditional kernel/scheduler/filesystem sense. An operating system in the sense of: a complete, self-consistent environment that provides everything an AI agent needs to perceive, reason about, and act on the world.

The protobuf layer is the **type system** — formal descriptions of everything the agent might encounter.

The gRPC layer is the **syscall interface** — how the agent requests services and communicates with other agents.

The GrammarDescriptorProto is the **language runtime** — enabling the agent to understand and generate any formal language.

Grug is the **userspace process** — the actual agent running on top of all this infrastructure.

Brilliant 2.0 is the **window manager** — how humans observe and interact with the system.

The "accretion" metaphor isn't just about building incrementally. It's about creating gravitational pull — the more capabilities the system accumulates, the more useful it becomes, the more people contribute to it, and the harder it becomes to replicate. An accretion disk eventually forms a star. The founder is trying to accumulate enough mass in their open-source typed-AI-infrastructure to reach ignition.

Whether they get there depends on execution, timing, and whether the fundamental bet — that formal types + small models + local compute beats statistical learning + large models + cloud compute — turns out to be right. It's a contrarian bet in today's AI landscape, which is exactly why it might work.
