# Projects

Projects we are working on, about to work on, or interested in that we can share and collaborate with in public. Mostly on GitHub.

Going to break these up into categories.

## Philosophy

We need to keep trying to be smart about decomposing these into projects that are manageable in size and scope, and proportionately valuable to the time we invest in them. Our approach has been bottoms-up since the beginning, and IMO the further we stray from that usually the more time we end up spending on work that turns out not to be useful, worthwhile, or have staying power. I think we are ready to start moving into the integration and training/inference stages now, but we still need to be incremental and tactical with how we spend our time.

### Current Focus

Right now I see our biggest opportunities in:
- Tool-tool integration
- Large-scope spec-driven development
- Local and semi-automated LoRA for "small specialists"
- Knowledge bases
- Grounding software development agents

### Integration Strategy

Many of these solutions exist in various forms already, and that's fine. We want to ensure they're adaptable to our stack involving mostly protobufs and open source software, by actually integrating them into gRPC services that we can call and compose with other software.

If they need more work to get there, we want to do that now that it's often pretty mechanical and easy (hey robot, here's two APIs, connect them — because this just became trivial it's precisely why now is the right time to do it at scale), or know what problems are in the way so we can plan for them. We're trying to make a ton of different software able to interoperate, and also build the software and skills/xp/tools that make that easier: that doesn't mean these aren't important but just setting expectations that if something ends up competing for time with more important stuff, we'll probably just drop it for now and go do that. I know that's an unfamiliar way to work for some people and I'm sorry about that.

## SQLite

Some of these surely exist in various forms already but many of the ones I checked either aren't mature or supported enough for me to feel comfortable building on top of (e.g., protobuf plugins) or didn't seem to be on the right track and maybe something we could just patch up/fork (sqlite-vec).

### CLI/gRPC Streaming for Tabular Data

- Simple gRPC streaming of CSV, XLSX, AVRO, Parquet, etc. into SQLite databases with their columns encoded as some kind of Protobuf
- Can just be stringly typed or strings-and-numbers, but worth looking into encoding DescriptorProtos instead (so I'm pretty sure we can just encode all these as DescriptorProtos), which are a superset of flat tabular types, but have the benefit of being able to be reflected or converted into .proto definitions

### Approximate Nearest Neighbor Search

- Good aKNN with SQLite — last I checked sqlite-vec was not actually building real indexes with their vectors, hadn't implemented HNSW fully, didn't really have full support for running in the browser with wasm and one of various sqlite-wasm tools, and otherwise didn't have good support for heavy use cases
- If they still don't seem like they're on a reasonable path to doing that we'll just need to look into solving this ourselves or without them
- I don't think HNSW or something more optimal than full table scans should take more than a week of work these days tbh

### Browser-based Vector Workloads

- SQLite-vec or some other tool for running similar vector+query workloads in the browser using WASM or WebGPU
- Bonus points for ONNX runtime compatibility since that's what Transformers.js uses

### Nested/Relational Protobuf Messages in SQLite

- Tooling for handling nested or relational protobuf messages in SQLite
- NOTE: I recently learned that GoogleSQL has an entire protobuf encoding of its query language and core data structures into proto itself, which is very aligned with what we'd been doing or thinking about already. I think we should see if a subset would work for SQLite and start there.
- IMO we're not going to get a perfect solution for this any time soon so I'm expecting to need to build a protobuf → SQLite partitioning and re-encoding (in their typed) system for now

### Vallkey Integration

- SQLite tools, especially for WAL and whatever those files Vallkey writes-through to are called

### Query Language Encoding

- A way to encode SQLite's type system and query language into EBNF or the GrammarDescriptorProto in our lexing/parsing tools in Gluon
- This project is ultimately for transpilation to/from protobuf and gRPC

### SQLite Resource Compendium

- A compendium of good tools/plugins/documentation/guides/resources/people/etc for being effective with SQLite
- Can literally just be a curated collection of readmes, PDFs, links, etc but actually vetted

## Protobuf

### Unicode Specification Encoding

- Convert the entire Unicode spec (note they are a bit weird about copyright) into something amenable to protobufs (literally every single one) into protobuf — see our `protosym` project but tbd if there is a better approach
- **Why:** Tokens literally often mean UTF-8 characters, so these form the base semantics for the string space that LLMs work within, and because basically every typed thing (including protobuf itself, or even EBNF if you read about it through a PDT) is downstream of Unicode due to it feeding into type systems through the types themselves, the language specs and documentation, and base types
- Also this should be very mechanical and something an organized approach should be able to do in one shot, ish. The main problem is actually the size of Unicode and how annoying their documentation is.

### Noto Fonts Encoding

- Encode all the Noto Fonts into protobuf/vectors (triple check legal first) as well as their underlying vector file types (IIRC there are two, one from Apple and another from Adobe, and they carry the scars of ancient IP battle wounds, hence Noto itself)
- This is how we ground unicode → glyphs → images like PDFs that models can parse
- Also it's cool that this literally turns all the unicode tokens into vectors, in a sense, and that it really is that simple to embed tokens into a 2D space by doing the same thing printers and PCs have been doing since the 80s…
- Another mostly mechanical project

### Font-to-Protobuf Mapping

- Try to map these font formats to a compact protobuf type corresponding to SVGs (ish — regular SVG like most markup is too verbose and has too many top-level structures, so we will slim down)
- Do the same with LaTeX and PDF if possible (may be able to use Gluon with LaTeX and our proto toolkit or image stuff for PDF)
- Once the lower-level pieces are in place, try to do the same with the image/audio processing from above

### Protobuf-based Monitoring UI

- (Can start before previous) I have some proof of concepts/ideas for a monitoring and charting UI system based on protobuf, SVG, and SQLite
- Early task to do before the bulk work is deciding if WebGPU is worth it — IMO the bottleneck will prob be transcoding and browser stuff, so prob not, but worth a check

### gRPC BiDi to Browser

- Encode and pass gRPC BiDi to the browser using WebRTC datachannels; there are proof of concepts out there and it seems quite do-able, just annoying because this stuff shouldn't be this hard
- I have some SCTP and other work that can be used for this that I can find; also see Golang Phion projects

### IANA/IETF Spec Parsing

- Parsing out the message types and protocols from all adopted IANA/IETF/etc specs currently still in use, extracting their wire formats and sequencing/semantics into a compact format, re-encoding as a protobuf message type as best as possible, then try to represent at least one real message or little thing
- See `email-rpc` and some other unpublished stuff of ours
- Let's get systematic about this

## Grug

The vision: A small-scale, simple, practical AI that can run locally and learn continuously.

### Grug Foundation Set

- Create a "simple language" dataset by having something like Sonnet or Kimi parse out a big dataset, like a sample of Common Crawl, into a very limited-vocabulary "caveman language" with labeled inputs/outputs
- Also take agent training/tool calling traces and perform the caveman language modifications on the prose of both inputs and outputs to try to keep actual problem solving in-distribution
- Together these form the **Grug Foundation Set**

### Grug Deep Fine-tuning

- Experiment with abliteration with deep fine-tuning of very small (Gemma 2B) models against the Grug Foundation Set with in-the-loop verification against simple tool-calling workloads (e.g., commands to call a command or use a tool with specific instructions, whatever makes sense if you grug)
- The goal is to enhance or preserve tool-calling abilities while allowing many of the "large language" capabilities to degrade or be lost entirely, since simple tool-calling models don't really need to know about Wittgenstein or Bostrom, and in fact if that kind of knowledge is taking up precious space in their weights that could go to knowing how to navigate go package installation errors, then begone with ye
- I also want to try giving Grug YouTube/Wikipedia/Google/GitHub access during this because I want the explore/exploit loop and tradeoff to be part of what Grug is training for. Grug think Hegel very confusing, need learn how to get just some knowledge before appreciate concept of absolute knowledge or volksgeist.

### Vision

- I'm quite confident we could train Grug out of a medium-size coding agent model with a lot of general knowledge left in its weights, but I want Grug to be able to run on small computers, because more Grug = more knowledge — Grug no need to know everything, just one thing and how to talk to other Grug
- If Grug no have human to talk to, Grug live simple life watching YouTube videos, encoding human data, and banging together rocks and sticks
- Basically I want Grug to be a prototype RL-at-home/continuous learning project that someone with a Mac mini could participate in training, and hopefully anybody with an iPhone could have their own Grug

### Challenges

- The deep fine-tuning of the base Grug is going to be the hard/costly part
- I think we maybe need a Big Grug first to help distill and steer training Little Grug
- **IMPORTANT:** Balancing the temptation to grug-maxx now and working on more boring stuff that will make it easier to confidently, effectively grug-maxx at scale with LLMs in the loop to handle the tasks that are too high-volume for us steer.
- We have to grug-maxx-maxx
