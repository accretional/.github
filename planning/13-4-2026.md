# Projects

Projects we are working on, about to work on, or interested in that we can share and collaborate with in public. Mostly on github

We need to keep trying to be smart about decomposing these into projects that are manageable in size and scope, and proportionately valuable to the time we invest in them. Our approach has been bottoms-up since the beginning, and IMO the further we stray from that usually the more time we end up spending on work that turns out not to be useful, worthwhile, or have staying power. I think we are ready to start moving into the integration and training/inference stages now, but we still need to be incremental and tactical with how we spend our time.

Right now I see our biggest opportunities in tool-tool integration, large-scope spec-driven development, local and semi-automated LoRa for "small specialists", knowledge bases, and grounding software development agents.

Also a note, I'm sure many if not all of these exist in various forms on their own already, and that's fine. We want to make sure they are adaptable to our stack involving mostly protobufs and open source software, by actually integrating them into grpc services that we can call and compose with other software. If they need more work to get there, we want to do that now that it's often pretty mechanical and easy (hey robot, here's two APIs, connect them - because this just became trivial it's precisely why now is the right time to do it at scale), or know what problems are in the way so we can plan for them. We're trying to make a ton of different software able to interoperate, and also build the software and skills/xp/tools that make that easier: that doesn't mean these aren't important but just setting expectations that it something ends up competing for time with more important stuff, we'll probably just drop it for now and go do that. I know that's an unfamiliar way to work for some people and I'm sorry about that.

## SQLite

Some of these surely exist in various forms already but many of the ones I checked either aren't mature or supported enough for me to feel comfortable building on top of (eg protobuf plugins) or didn't seem to be on the right track and maybe something we could just patch up/fork (sqlite-vec).

- CLI/simple gRPC streaming of CSV, XSLX, AVRO, Parquet, etc into sqlite databases with their columns encoded as some kind of Protobuf - can just be stringly typed or strings-and-numbers but work looking into encoding DescriptorProtos instead, which are a superset of flat tabular types (so I'm pretty sure we can just encode all these as DescriptorProtos) but have the benefit of being able to be reflected or converted into .proto definitionsx

- Good aKNN with sqlite, last I checked sql-vec was not actually building real indexes with their vectors, hadn't implemented HNSW fully, didn't really have full support for running in the browser with wasm and one of various sqlite-wasm tools, and otherwise didn't have good support for heavy use cases. If they still don't seem like they're on a reasonable path to doing that we'll just need to look into solving this ourselves or without them. I don't think HNSW or something more optimal than full table scans should take more than a week of work these days tbh.

- Also yeah, sqlite-vec or some other tool for running similar vector+query workloads in the browser using wasm or web gpu or something. Bonus points for ONNX runtime compatibility since that's what Transformers.js uses

- Tooling for handling nested or relational protobuf messages in sqlite. NOTE: I recently learned that googlesql has an entire protobuf encoding of googlesql's query languages and core data structures into proto itself, which is very aligned with what we'd been doing or thinking about already. I think we should see if a subset would work for sqlite and start there. IMO we're not going to get a perfect solution for this any time soon so I'm expecting to need to build a protobuf -> sqlite partitioning and re-encoding (in their typed) system for now.

- Vallkey : sqlite tools, especially for WAL and whatever those files valkey writes-through to are called.

- A way to encode SQLite's type system and query language into EBNF or the GrammarDescriptorProto in our lexing/parsing tools in gluon. This project is ultimately for transpilation to/from protobuf and grpc

- A compendium of good tools/plugins/documentation/guides/resources/people/etc for being effective with sqlite. Can literally just be a curated collection of readmes, PDFs, links, etc but actually vetted.

## Protobuf

- Convert the entire Unicode spec (note they are a bit weird about copyright) into something amenable to protbufs (literally every single one) into protobuf, see our protosym project but tbd if there is a better approach. The idea is that this will help with grounding given that "tokens" literally often means UTF-8 characters so these form the base semantics for the word of strings that LLMs work within, and because basically every typed thing (including protobuf itself, or even ebnf if you're ready about it through a pdt) is downstream of Unicode due to it feeding into type systems through the types themselves, the language specs and documentation and base types. Also this should be very mechanical and something an organized approach using should be able to do in one shot, ish. The main problem is actually the size of Unicode and how annoying their documentation is.

- Encode all the Noto Fonts into protobuf/vectors (triple check legal first) as well as their underlying vector file types (IIRC there are two, one from Apple and another from adobe, and they carry the scars of ancient IP battle wounds, hence Noto itself). This is how we ground unicode->glyphs->images like PDFs that models can parse. Also it's cool that this literally turns all the unicode tokens into vectors, in a sense, and that it really is that simple to embed tokens into a 2d space by doing the same thing printers and pcs have been doing since the 80s… Another mostly mechanical project.

- Try to map these font formats to a compact protobuf type corresponding to SVGs (ish, regular svg like most markup is too verbose and has too many top-level structures, so we will slim down). Do the same with Latex and Pdf if possible (may be able to use gluon with latex and our proto toolkit or image stuff for pdf). Once the lower level prices are in place try to do the same with the image/audio processing from above.

- (Can start before previous) I have some proof of concepts/ideas for a monitoring and charting UI system based on protobuf, SVG, and sqlite. Early task to do before the bulk work is deciding if webgpu is worth it. IMO the bottleneck will prob be transcoding and browser stuff, so prob not, but worth a check

- Encoding and pass gRPC BiDi to the browser using webRTC datachannels, there are proof of concepts out there and it seems quite do-able, just annoying because this stuff shouldn't be this hard. I have some SCTP and other work that can be used for this that I can find, also see Golang phion projects.

- Project: parsing out the message types and protocols from all adopted IANA / IETF / etc specs currently still in use, extracting their wire formats and sequencing/semantics into a compqct format, re-encoding as a protobuf message type as best as possible, then try to represent at least one real message or little thing. See email-rpc and some other unpublished stuff of ours. Let's get systematic about this

## Grug

- Create a "simple language" dataset by having something like sonnet or kimi parse out a big dataset, like a sample of common crawl, into a very limited-vocabulary "caveman language"with labeled inputs/outputs. Also take agent training/tool calling traces and perform the caveman language modifications on the prose of both inputs and outputs to try to keep actual problem solving in-distribution. Together these form the Grug Foundation Set

- Experiment with abliteration with deep fine tuning of very small (Gemma 2b) models against the Grug foundation set with in-the-loop verification against simple tool-calling workloads (eg commands to call a command or use a tool with specific instructions, whatever makes sense if you grug). The goal is to enhance or preserve tool-calling abilities while allowing many of the "large language" capabilities to degrade or be lost entirely, since simple tool-calling models don't really need to know about Wittgenstein or Bostrom, and in fact if that kind of knowledge is taking up precious space in their weights that could go to knowing how to navigate go package installation errors, then begone with ye. Grug respect man who think long time and find good stuff, but Grug live simple live banging binaries together. I also want to try giving Grug YouTube/wikipedia/google/github access during this because I want the explore/exploit loop and tradeoff to be part of what grug is training for. Grug think Hegel very confusing, need learn how to get just some knowledge before appreciate concept of absolute knowledge or volksgeist.

- I'm quite confident we could train Grug out of a medium size coding agent model with a lot of general knowledge left in its weights, but I want Grug to be able to run on small computers, because more grug = more knowledge, Grug no need to know everything, just one thing and how to talk to other grug. If grug no have human to talk to, grug live simple life watching YouTube videos, encoding human data, and banging together rocks and sticks. Basically I want grug to be a prototype rl-at-home/continuous learning project that someone with a Mac mini could participate in training, and hopefully anybody with an iPhone could have their own Grug.

The deep fine tuning of the base grug is going to be the hard/costly part. I think we maybe need a Big Grug first to help distill and steer training Little Grug.
